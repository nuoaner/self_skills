## 1. 为什么保留

课程制作中常遇到口语化、不完整或修改边界不明确的需求，例如“这页 PPT 太空”“流程箭头不对”“补充知识点，但别搞得太复杂”。`project-prompt-polisher` 的职责是先把这些说法转换成可执行的制作任务，明确目标、对象、范围、保留项、验收标准和验证方式，降低误解和返工。

**能力边界**：原 Skill 面向 Codex、AI 编程和工程交接；把它用于课程时，只借用“需求规范化”方法。教学内容本身仍需由教案、课程资料和专门的教学/PPT Skill 处理。

## 2. 建议加入的课程制作流程

```text
原始需求 / 教案 / 参考课件
    ↓
project-prompt-polisher（需求整理与边界确认）
    ↓
教学任务规格（目标、知识点、受众、课时、教学活动、制作约束、验收方式）
    ↓
课程专用 Skill（教案、课件结构、讲授逻辑、版式、配图）
    ↓
知识准确性检查 + 教学可理解性检查 + PPT 渲染与排版验收
    ↓
交付与迭代记录
```

## 3. 教学场景必须补充的维度

| 维度 | 需要明确的内容 |
| --- | --- |
| 受众与目标 | 学员基础、年级或岗位、先修知识、课时与可检验的学习目标 |
| 内容范围 | 必讲概念、知识覆盖、可选延伸、教材或来源，避免无依据增加事实 |
| 单概念讲解 | 说明它是什么、有什么作用、输入/输出是什么、如何工作，并提供具体例子 |
| 关系图 | 分清组成关系、步骤流程、状态迁移；箭头方向与含义必须正确 |
| 可视化 | 对抽象概念使用图示/案例；缺少可信图片时明确保留占位区 |
| 教学表达 | 语言自然，减少空话；标题简短；不要为制造对比而用“不是……而是……” |
| 页面密度 | 先保证知识讲清楚，再确定页数；留白与信息密度都以可讲授为准 |
| 可追溯性 | 关键数据、定义、图片、引用保留来源或待核实标记 |
| 验收 | 覆盖率、准确性、学员能否理解、演示时长、文字溢出、图文对齐、箭头准确、文件可编辑和可播放 |

## 4. 一个实际使用示例

**口语需求**：“具身智能这页太空了，箭头也有问题，你帮我优化一下。”

**整理后的任务重点**：

- **目标**：在保持该节原有教学目标的前提下，提高这一页的讲授完整度和图示准确性。
- **修改范围**：仅修改指定页及与该页直接相关的讲解备注；不重排整套课程。
- **知识要求**：列出本页应讲清的核心概念及必要示例；凡含专业术语，补充职责、输入输出和工作机制。
- **图示要求**：确认图中表示的是组成、流程还是状态；各箭头有明确方向和语义，不以装饰箭头替代关系说明。
- **版式要求**：标题简短，信息区布局均衡，增加有教学价值的内容，不靠无关装饰填充。
- **不变项**：原课程知识体系、受众定位、既定模板/品牌、其他页面与可验证事实。
- **验收标准**：知识点没有遗漏或臆造；图示关系能逐节点解释；无文字溢出；在目标投影比例下可读；提供渲染截图和修改清单。
- **待确认**：当教案、原图或来源缺失且会影响修改正确性时，单独列出，不猜测。

## 5. 推荐调用方式

```text
先参照 project-prompt-polisher 整理我下面这段课程需求，
输出一份可直接交给课程 PPT Skill 的任务说明。
保留我的原意，补齐教学目标、知识范围、图示关系、
保留项、验收要求和需确认事项。
这一轮只整理需求，不直接制作 PPT。
```

实际制作阶段再选择对应课程/PPT Skill。若用户已经提供了完整需求，不应机械增加一次“打磨提示词”步骤。

## 6. 维护约定

- 保留原 `project-prompt-polisher` 作为通用需求澄清工具，不修改原 Skill 的工程专用检查器和触发边界。
- 课程专用的教学质量标准保存在本文件，未来可作为新课程工作流或现有课程 Skill 优化的参考。
- 如果后续确认这个流程频繁使用，再考虑将教学场景整合进专门的课程 Skill；避免为同一职责重复创建多个 Skill。
- 以 GitHub 仓库为长期可追溯的保存位置；本记录不意味着已自动安装到 ChatGPT 的个人 Skills 库。
