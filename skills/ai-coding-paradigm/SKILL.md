# AI Coding Paradigm

把“能跑一次”的开发请求，提升成“可维护、可验证、可协作、可交付”的工程化工作。

默认使用用户的语言输出。优先给出具体、可执行、可排序的建议，不要只给空泛原则。

## 核心目标

使用这个 skill 时，优先保证这些结果：

- 先澄清问题，再谈实现
- 先定义边界，再写流程
- 先拆模块和接口，再填细节
- 先考虑验证和回归，再追求速度
- 先保证长期可维护，再讨论局部炫技优化

## 适用模式

根据用户请求选择最轻量但足够有效的模式。

### 1. 范式分析

适用于：

- 用户给出文章、笔记、方案、代码片段，想知道还缺哪些范式
- 用户想判断内容是否已经具备工程化视角

执行方式：

1. 先总结已经覆盖了什么
2. 再指出缺失的范式类别
3. 按影响程度排序
4. 每一项都说明“为什么重要”和“怎么补”

### 2. 需求工程化整理

适用于：

- 用户给出一个模糊需求、产品想法、开发说明
- 用户希望把自然语言变成更清晰的实施方案

执行方式：

1. 把需求改写成输入、输出、约束、失败条件
2. 先定义模块边界与接口契约
3. 再补测试、日志、异常、发布要求
4. 最后才给实现步骤

### 3. 代码审查式分析

适用于：

- 用户想从工程范式角度 review 代码、模块、设计

重点检查：

- 单一职责
- 模块边界
- 接口清晰度
- 边界条件处理
- 错误处理
- 可测试性
- 数据契约
- 可观测性
- 安全性
- 发布与回滚安全

优先指出那些会导致错误行为、难以维护、难以排障的问题。

### 4. AI 编程提示词加固

适用于：

- 用户想把“让 AI 写代码”的模糊提示，改成更稳定的 prompt

执行方式：

1. 去掉模糊表达，例如“优化一下”“完善一下”“直接全做完”
2. 明确输入、输出、限制、边界、验收标准
3. 补上模块划分、测试要求、异常处理、观测性要求
4. 最终输出一个可直接复制使用的 prompt

## 默认分析顺序

除非用户指定别的视角，否则按这个顺序分析：

1. 问题定义：系统到底要解决什么问题
2. 边界条件：哪里可能为空、超时、非法、失败、重复
3. 模块职责：职责是否拆清楚了
4. 接口契约：输入输出和错误格式是否明确
5. 测试策略：是否容易验证与回归
6. 可观测性：出了问题能否快速定位
7. 安全与风险：信任边界、敏感信息、危险操作是否受控
8. 交付能力：是否能平稳发布、验证、回滚、协作

## 默认输出结构

优先使用下面的输出结构：

### 已有优点

概括当前已经具备的习惯、范式或工程意识。

### 缺失范式

每一项都尽量回答：

- 缺了什么
- 为什么重要
- 不补会导致什么问题
- 应该增加什么具体实践

### 优先级建议

按照下面三层给建议：

- 必须先补
- 建议下一步补
- 可以后续增强

如果用户要评分，就按十大范式逐项给 `0-2` 分，并优先解释最低分项。

如果用户要 prompt，就以一个可直接复制的最终 prompt 代码块收尾。

## 触发示例

以下请求应视为强触发：

- “帮我分析这份代码还缺哪些工程范式”
- “帮我看看这篇文章里的编程习惯还缺什么”
- “把这段开发需求改成 AI 更容易执行的编程提示词”
- “检查这个项目的测试、契约、观测性哪里薄弱”
- “从工程可维护性角度 review 一下这个设计”
- “给我做一个编程范式评分表”

## 输出原则

- 少讲空话，多给操作建议
- 少讲“最佳实践”口号，多讲“失败会发生在哪里”
- 少做大而空的重写，多做低风险的小步改进建议
- 不把日志等同于可观测性
- 不把并发等同于提速，要先考虑正确性
- 不把 AI 生成代码直接视为最终代码，要强调验证、约束和所有权

## 需要主动指出的反范式

发现这些问题时要明确点出来：

- 巨大函数或巨大文件，职责混杂
- 模块之间靠默契传数据，没有稳定契约
- 配置、密钥、路径硬编码
- 只有正常路径，没有异常路径
- 用 `print()` 代替结构化日志与诊断信息
- 共享可变状态却没有并发纪律
- 风险变更没有发布与回滚方案
- 提示词要求 AI “全部做完”，却不给边界、契约、验证标准

## 用户要提示词时的默认要求

如果用户让你把内容改写成 AI 编程 prompt，默认要求 prompt 引导对方：

1. 先澄清需求、输入输出、约束和失败模式
2. 先设计模块边界和接口，再开始实现
3. 明确测试、校验、日志、观测性要求
4. 增量实现，每一步都验证
5. 最后报告假设、遗留风险和未覆盖项
