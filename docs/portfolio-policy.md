# self_skills Core / Lab 治理规则

**维护策略 C：自己和团队使用优先，真实效果稳定后再公开。** 本文定义仓库自己的发布政策；它不是 OpenAI 平台要求。

## 单一事实来源

[分类数据](../skills/catalog.json) 是唯一有效的分层与处置数据；[可读清单](../skills/CATALOG.md) 由 `python scripts/catalog.py sync` 生成，`check-docs` 用于检查同步。旧 README 的 Productionized / Visual Lab 数量只是历史基线，不再用于发布筛选。

| 分层 | 含义 | 使用方式 | 允许状态 |
|---|---|---|---|
| Core | 优先维护的专业能力候选 | 按需安装单个完整 Skill；不代表 A/B/C 测试已通过 | retain / strengthen |
| Lab | 实验、新方向、旧 Skill 的独立性观察或合并候选 | 仅显式测试；缺 frontmatter 的内容是草案，不能当正式 Skill 安装 | retain / strengthen / merge_candidate / retire_candidate |
| Reference | 外部索引、选型资料 | 仅阅读，不作为 Skill 安装 | index_only |

“Core”不等于“高分”、“稳定提升”或“ChatGPT 认证”。首次分类基于代码审阅、实际业务场景和可辨别的差异化价值；`agent_evidence: not_measured` 表示缺少仓库内可复验的真实模型运行证据。

## 价值判断（先做减法）

评估独立 Skill 前先回答：

1. 去掉 Skill 后，Agent 是否会失去专门知识、已验证规则、资产或确定性工具？若仅失去“先分析再执行”等通用提醒，优先迁移到项目 `AGENTS.md` 或删除冗余说明。
2. 触发范围是否对应清楚的用户任务，而不是“任何开发”“所有图片”等大类别？是否挤占其他 Skill 的任务？
3. 有无至少两个符合场景、两个易混淆反例，以及一个带明确验收条件的任务？
4. 实际使用记录是否显示更好的成功率、质量、安全性或执行成本？如果没有证据，先留 Lab，不因印象评分提升成熟度。
5. 为了维护它需要多少同步文档、专有路径、过时 API 和权限？是否能合并为已有 Skill 的按需引用？

**核心升格门槛：** 结构与工具检查通过；可公开材料来源合规；正反触发案例齐全；真实 A/B/C 对照完成且指标与原始证据可追溯；没有新的重大安全或兼容性回归。小样本时要展示方差与失败例，不凭一次成功“认证”。

## 本轮去留方向（待效果验证）

- `ai-coding-discipline`：优先评估将通用编码约束转为项目级 `AGENTS.md`，保留有专业增量的安全规则。
- `project-structure-review`：考察并入 `ai-coding-paradigm` 的交付审查模式。
- `creative-reference-analyzer`：考察并入 `visual-story-image-director` 的参考图分析环节。
- `ai-image-quality-reviewer`：考察转为视觉共享 QA 参考资料。
- `client-technical-reporting`：考察由强制 Skill 转为可选客户报告模板。
- `image-prompt-engineer`：优先评估退出独立 Skill；通用生图说明可能足以交由模型完成。
- `image-generation-collection`：定位为第三方索引，保持来源署名，禁止混入安装包。

上面是**候选决定**，不是已删除的文件或验证过的性能结论。

## 实际使用证据如何收集

[评测说明](../evals/README.md) 使用 A（不装）、B（旧版）、C（新版本）三组，尽量固定模型、工具授权、任务材料及评分规则。比较正向触发、误触发、任务成败、验收质量、不必要确认、时间、工具数、安全事件和有来源的 Token 使用。`evals/cases.jsonl` 是案例规格，不是运行成绩。对于视觉输出，额外做身份/文本/素材一致性人工复核。

日常团队可填写 `evals/usage-log.template.csv` 的字段，**勿提交原始客户资料或密钥**。没有使用量数据就标记“未知”，不把“没有记录”解释为“从未使用”。

## 兼容迁移与安全退出

1. 先冻结拟合并／拟淘汰 Skill 的公开名称、输入、输出、引用路径与素材。
2. 在候选目标中验证主要场景可以覆盖（包括不启用 Skill 的对照）。明确不能迁移的案例。
3. 提供迁移映射与恢复方式；原目录和名称在过渡期不直接删除或改名。
4. 只有效果证据支持、资源均已归档或迁移、实际使用方能够切换时，才提交单独的移除 PR，并在合并前取得明确授权。
5. 如果实验反证“合并更差”，撤销合并决定；不要为了减少数量而损失独立价值。

发布到公开 Skill 时单独检查版权、素材授权、第三方源码、敏感信息、工具依赖和实际可安装性。只公开仓库内经过审查的子目录，不公开内部客户资源。模型新版本发布本身不是一次重写的理由。

**当前状态：** 仅先落地分层、规范、用例及非破坏性工具；尚无真实运行数据，不能据此删除 Skill。
